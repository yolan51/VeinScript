## The pitch

VeinScript is a language where the building block of a program isn't an object or a function. It's an identity. You declare the data an identity can carry, called shapes and written with a dollar sign. You declare the tags it can wear, called marks and written with a hash. And you declare the messages it can send, called events and written with an at sign. All behaviour lives in shards, and a shard never calls anything. It targets every identity that matches and acts on each one. When two shards write the same field in the same tick, the field itself says how the writes combine, for example 'folds sum', so the order the shards run in never matters. The same model runs a game loop, a chat across three console windows, and a website assembled from fragments. It comes with one compiler, an interpreter and a C# backend, plus a desktop IDE that lets you step through time and watch your identities change one tick at a time.

## The mental model

**Everything is an identity.** Behaviour never calls behaviour. A program makes identities with `spawn()` and hangs data and tags on them. Behaviour then *finds* them with a query.

- **Shape `$Health`**: the fields an identity carries (a component), e.g. `attach $Health to e { hp: 5 }`.
- **Mark `#Enemy`**: a tag with no fields, e.g. `mark e #Enemy` / `unmark`. `$Enemy` and `#Enemy` are two different things.
- **Event `@Damaged`**: a message with a payload. `emit` queues it and `hear @Damaged as d { … }` reacts to it. Every event carries provenance (`d.from.name`, `d.cause`).
- **Shard**: the only place behaviour lives. It is a set of blocks: `run once`, `each tick`, `settled`, `every N`, `hear @E`. Inside a block, `target $Health #Enemy as self { … }` visits every identity that carries all of those.
- **SF / fn**: an `SF` is a named sequence of emits and never returns. An `fn` computes a value and returns it.
- **Builder + bring**: a template. The *name of its output field* decides what it makes: `markup`→`@Html`, `css`→`@Style`, `code`→`@Script`, `line`→`@Print`, and no output field→`@BuilderName`. A `mark` member makes it an identity template, so `bring Unit(10, 6)` does spawn + attach + mark. `$Shape` includes copy a shape's fields into the parameter list, and arguments bind by position.
- **Bundle**: the module, written `bundle Game by you { … }`. Everything in it is private by default. Only `shared("…")` members of a `publicator` can be used from another bundle, either as `*Author.Bundle.Publicator.member` or as a bare name after `need "Author.Bundle"`. An `app` manifest `load`s bundles. The first one is the principal, and its `start @E` is the only boot event. The others join the same runtime.

**Time: tick → commit → settled.**
1. `run once` seeds the world.
2. Every `each tick` block runs. A write to a field is a *contribution*, and the shape says how contributions merge. With `hp: int folds sum`, two shards that each do `hp -= 1` give `hp - 2`, whatever order they ran in.
3. `spawn` happens immediately. `attach`/`unattach`/`mark`/`unmark`/`destroy` wait for the commit point, so no shard ever sees a half-changed world.
4. `settled` runs after the folds are reconciled. That is where you read final values, such as death checks.

Events drain one at a time. Each event's structural changes are committed before the next event runs, so the next event sees what the last one built. Inside the event that made a change, the change is not visible yet.

**Two execution models, one identity model.** The reactive loop covers `emit`/`hear`/`ShardView` → `@Response`, console and network. The ECS tick loop covers `target`/`each tick`/`settled`/`folds` and is driven by `--ticks N`. Both run in the interpreter. The identity half also compiles to C# with `veinc emit`.

## The four sigils

| sigil | names | example | means |
|---|---|---|---|
| `$` | Shape | `$Health` | Data an identity carries, as fields (a component). `attach $Health to e { hp: 5 }` |
| `#` | Mark | `#Enemy` | A tag with no fields. `mark e #Enemy`, `unmark e #Enemy` |
| `@` | Event | `@Damaged` | A message with a payload. `emit` queues it and `hear @Damaged as d { … }` reacts |
| `&` | Builder | `&Heading` | A template, referenced by name, e.g. `*Vein.Web.Elements.&Heading(…)`. A local one is used as `bring Unit(10, 6)` |

## Lesson 1. Two shards, one `hp` ★

**Goal:** Read a complete VeinScript program: shapes carry data, marks tag identities, shards `target` every match, and `folds sum` merges writes made in the same tick.  
**Length:** about 6 min  
**Samples:** `samples/entities.vein`

**Open with:** Two pieces of code, neither knows the other exists, and both subtract one from the same number in the same frame. In most languages one write wins or you reach for a lock. Here the number drops by exactly two, every time, whichever runs first.

### Say

- `shape $Health` declares data an identity can carry, and `hp: int folds sum` says what happens when several shards write `hp` in one tick: their deltas are added.
- `run once` seeds the world. Inside `repeat 3`, `spawn()` makes a new identity, `attach $Health to e { hp: 5 }` gives it data, and `mark e #Enemy` tags it. `$` means shape, `#` means mark.
- Drain and Poison are two separate shards with the same line: `target $Health #Enemy as self { self.Health.hp -= 1 }`. Neither calls the other, and neither knows the other exists.
- `target` is the loop over identities: it visits every identity carrying both `$Health` and `#Enemy`, and `self.Health.hp` reads that identity's field.
- The Undertaker reads `hp` in `settled`, which runs after the tick's writes are reconciled, so the value it sees is final. At zero or below it does `mark self #Dead` and `unmark self #Enemy`. `Entity` is the id of the identity the loop is on.
- Run it for three ticks: every enemy prints hp 3, then 1, then -1, then 'died'. That is 5 minus 2 per tick, so both writes landed.
- Live: delete `folds sum` and run again. Now hp falls by only one per tick, so a write was silently lost, and `veinc exec` on the edited file flags a Drain x Poison conflict on `$Health.hp`. Put `folds sum` back.

### Show — `samples/entities.vein` lines 13–38
Data, a seeded world, and two shards writing the same field

```vein
shape $Health {
    hp: int folds sum      // many shards may drain hp in one tick; sum the deltas
}

shard Spawner {
    // `run once` builds the world before anything else happens.
    run once {
        repeat 3 {
            let e = spawn()
            attach $Health to e { hp: 5 }
            mark e #Enemy
        }
    }
}

shard Drain {
    each tick {
        target $Health #Enemy as self { self.Health.hp -= 1 }
    }
}

shard Poison {
    each tick {
        target $Health #Enemy as self { self.Health.hp -= 1 }
    }
}
```

### Show — `samples/entities.vein` lines 40–53
Reading the result after the tick settles

```vein
shard Undertaker {
    // settled runs AFTER the tick's contributions reconcile — the only place a death check is
    // correct, because during the tick another shard may still be subtracting.
    settled {
        target $Health #Enemy as self {
            emit *Vein.Console.Io.@Print { text: "enemy " + Entity + " hp " + self.Health.hp }
            if self.Health.hp <= 0 {
                mark self #Dead
                unmark self #Enemy
                emit *Vein.Console.Io.@Print { text: "enemy " + Entity + " died" }
            }
        }
    }
}
```

### Watch out

- Use `veinc run … --ticks 3` on camera. The header's `veinc render` line prints an emit trace instead of the hp lines.
- Removing `folds sum` still passes `veinc check`. Only the run and `veinc exec` show the lost write, so rehearse the edit on a copy.
- Read a `folds` field in `settled`. A mid-tick read is not reconciled yet (RULES 13).
- `#Enemy` and `#Dead` are never declared, so their names go unchecked and a typo would silently create a new mark (RULES 16).
- With no `spawn()` the world is empty and every `target` matches nothing (RULES 10).
- The lines print through `emit *Vein.Console.Io.@Print`. Don't explain it yet: l04 reveals that printing is an event.

## Lesson 2. `bring`: one line per identity ★

**Goal:** Declare an identity template with `builder … { $Shape   mark #Mark }` and create identities with `bring`, including `bring N`.  
**Length:** about 3 min  
**Samples:** `samples/entities_template.vein`

**Open with:** Last lesson took three lines to make one enemy: spawn, attach, mark. A builder does it in one line. `bring Mob(12)` lowers to exactly those three statements, and `bring Unit(12, 6)` to four, with one attach per shape.

### Say

- `builder Unit { $Health $Shield   mark #Unit }` has no body. The shapes and the mark it lists are its whole definition.
- The `mark` member makes it an identity template: `bring Unit(12, 6)` means spawn, attach `$Health` with hp 12, attach `$Shield` with sp 6, and mark `#Unit`.
- Arguments bind by position across the includes in declaration order: `$Health` takes hp, then `$Shield` takes sp. `Mob` and `Ward` include one shape each, so they take one argument.
- `bring 2 Unit(4, 2)` makes two separate identities, e4 and e5, not one shared one.
- Wear targets `$Health $Shield #Unit`, and several shapes in one query is an AND. After tick one e1 reads `hp=11 sp=4`, while e2 (a Mob) and e3 (a Ward) never change, because neither carries both shapes.
- Live: `veinc scaffold samples/entities_template.vein Unit` prints a ready-to-paste `bring Unit(` call with one slot per field, each labelled with its type and the shape it came from.

### Show — `samples/entities_template.vein` lines 39–65
Two shapes, three one-line templates, and a shard that uses them

```vein
shape $Health { hp: int folds sum }
shape $Shield { sp: int folds sum }

// Three templates over two shapes. What an identity CARRIES is the template's whole definition —
// there is no body and nothing to run, which is what keeps a template a declaration rather than a
// little constructor with its own rules.
builder Unit { $Health $Shield   mark #Unit }
builder Mob  { $Health           mark #Unit }
builder Ward { $Shield           mark #Unit }

shard Seed {
    run once {
        bring Unit(12, 6)
        bring Mob(12)
        bring Ward(6)
        bring 2 Unit(4, 2)     // the count makes two separate identities, not one shared
    }
}

shard Wear {
    each tick {
        target $Health $Shield #Unit as self {
            self.Health.hp -= 1
            self.Shield.sp -= 2
        }
    }
}
```

### Watch out

- Without a `mark` member, or a mark carried by an included shape (RULES 15c), a `$Shape` include only copies fields. `bring Mob(12)` then emits `@Mob`, attaches nothing, and `target $Health` never sees it. `veinc check` warns VS0237 when nothing hears that event (RULES 8).
- Ask `veinc scaffold` for the argument order instead of counting (RULES 9). Keep the header's scaffold listing off screen: it shows `?` slots, while the real command prints `base, // hp: int from $Health REQUIRED — give it a value`.
- `bring 2 Unit(…) as n` is VS0222, because a count cannot be combined with `as` (RULES 7b).
- A builder's output field decides what it makes, and a `mark` member makes an identity (RULES 5, 7).

## Lesson 3. Nothing changes mid-frame ★

**Goal:** Predict when structural changes land: `spawn` is immediate, while attach, unattach, mark, unmark and destroy wait for the commit point, and `settled` sees the result.  
**Length:** about 4 min  
**Samples:** `samples/entities_destroy.vein`

**Open with:** Three shards remove things this frame, and a fourth, running in the same frame, counts what's left. It sees nothing removed, and that is the guarantee, not a bug.

### Say

- `mark #Alive` and `mark #Guarded` on their own lines, outside any shard, declare the two marks. Lesson 1 never declared `#Enemy`. Declaring any mark makes the compiler check mark names in this bundle, and lesson 11 comes back to that. `builder Mob { $Health, $Shield   mark #Alive   mark #Guarded }`: each of the three `bring Mob(…)` calls gives an identity both shapes and both marks, with hp 10, 20 and 30.
- Three removal verbs of three sizes: Cull does `unmark m #Alive` under 15 hp, Disarm does `unattach $Shield from m`, and Reap does `destroy m` over 25 hp.
- During counts in `each tick`, the same phase as the removals, using `var alive = 0` counters. `var` declares a local you reassign (`alive = alive + 1`), while lesson 1's `let e = spawn()` names a value you don't mean to change (the compiler does not enforce that today). After runs the identical counts in `settled`.
- Frame 1 prints `during   alive 3   shielded 3   entities 3`, then `after    alive 1   shielded 0   entities 2`. Every removal was queued and landed together at the commit point.
- The 10-hp mob still exists, it just isn't `#Alive`. The 30-hp one is gone completely. That's why `entities` is 2 and `alive` is 1.
- Live: cut shard During, paste it above Cull, and run again. The numbers don't change: no shard ever sees a half-changed world, so shard order can't matter.
- Live in the Workbench: open the file, go to the Runtime panel, press Boot, then Step ▸ once, and watch the entity browser go from three identities to two.

## Lesson 4. Printing was an event all along ★

**Goal:** Write a reactive program: name and declare a boot event, `hear` events with an `as` binding, and `emit` events with payloads.  
**Length:** about 3 min  
**Samples:** `samples/console.vein`

**Open with:** Every line we've printed so far was an `emit`. Nothing in VeinScript calls the terminal. The terminal is just another listener.

### Say

- `bundle App { … }` wraps the whole program. A bundle is VeinScript's module (lessons 1-3 had one too, just off-screen), and with no `by` in its header (compare `bundle Store by you {`) its author is `local`. Inside it, `start @Boot { }` names the entry event, `event @Boot { }` declares it, and `veinc run` fires it once.
- Shard Main is only two `hear` blocks, with no `run once` and no `each tick`. Unlike the clock-driven shards so far, it does nothing until an event arrives.
- `emit *Vein.Console.Io.@Print { text: … }` writes a line, and `hear *Vein.Console.Io.@Input as i` fires once for each line you type. Nothing writes to stdout or reads stdin directly: even the `print` helper you'll see in lesson 5 is an SF that just emits @Print.
- Read the path left to right: `*` starts it, `Vein` is the author, `Console` the bundle, `Io` the publicator, and `@Print` the event.
- `as i` binds the payload, so `i.text` is the typed line, and `+` joins strings.
- Live: run it, type `hello` and get `you said hello`, type one more line, then end with Ctrl+Z and Enter on Windows (Ctrl+D on Unix).

### Show — `samples/console.vein` lines 7–19
A whole interactive program: one entry event, one shard, two handlers

```vein
bundle App {
    start @Boot { }        // this program's entry — fired once when it runs
    event @Boot { }

    shard Main {
```

## Lesson 5. `fn` computes, `SF` emits ★

**Goal:** Choose between `fn` (returns a value) and `SF` (a named sequence of emits), and call shared ones from another bundle by qualified path.  
**Length:** about 3 min  
**Samples:** `samples/functions.vein`

**Open with:** VeinScript has functions, two kinds of them, and the split is not about syntax. It's about what they produce: a value, or events.

### Say

- `fn bonus(streak: int) return int` computes and returns, so it can go anywhere a value can. Parameters are written `name: Type`.
- `SF announce(label: string, value: int)` has no return type, and its body is an `emit`. An SF is a named emit sequence, and a call to it stands alone as a statement.
- `fib` is a local `fn` that recurses. It needs no `shared` to be called inside this bundle.
- `shared("…")` inside a `publicator` is the only thing that crosses a bundle boundary, and the string is a label shown in completion.
- Scoreboard calls `announce("fib(10)", fib(10))`, an fn result passed into an SF call, and the output reads `fib(10): 55` after `streak 3 bonus: 15` and `streak 99 bonus: 50`.
- Across bundles: `*Vein.Math.Scalars.clamp(99.0, 0.0, 10.0)` is Vein.Math's shared fn and prints `clamp(99, 0, 10) = 10`, and `*Vein.Console.Io.print(…)` is Vein.Console's shared SF, which emits @Print for you.

### Show — `samples/functions.vein` lines 20–42
A shared fn, a shared SF, and a local recursive fn

```vein
publicator Api {
    // A `fn` returns — so it can be used wherever a value can. This one is `shared`, which means
    // another bundle could call it as *you.Functions.Api.bonus(…).
    shared("Score bonus for a streak, capped at 50.")
    fn bonus(streak: int) return int {
        if streak <= 0 { return 0 }
        if streak > 10 { return 50 }
        return streak * 5
    }

    // An `SF` emits — it names an intent so callers don't hand-assemble the event every time.
    shared("Announce a score to the console.")
    SF announce(label: string, value: int) {
        emit *Vein.Console.Io.@Print { text: label + ": " + value }
    }
}

// A local `fn` needs no `shared` — that keyword is about crossing bundles, not about being callable
// here. `fn` may recurse.
fn fib(n: int) return int {
    if n <= 1 { return n }
    return fib(n - 1) + fib(n - 2)
}
```

Four kinds of call: local and cross-bundle, fn and SF

## Lesson 6. A website assembled from events ★

**Goal:** Serve a site with several routes and a form, where shards contribute `@Html` fragments per route and a `ShardView` assembles the response.  
**Length:** about 4 min  
**Samples:** `samples/web_site.vein`

**Open with:** No handler in this site returns a page. Shards emit fragments, one view listens, and the page is whatever arrived.

### Say

- `need "Vein.Web"` makes the stdlib builders `Heading`, `Paragraph` and `Link` usable by bare name. None of them has a `mark` member. Each has a `markup = …` output field instead, and a builder's output field name decides what it makes. So `bring Heading("Say hello")` spawns no identity and writes no markup: it queues an @Html fragment. A `css` field would make @Style, `code` @Script and `line` @Print.
- Routing is a plain `if r.path == "/greet"`. Every page shard hears every @Request and only contributes when its path matches.
- Same path, two methods. On GET, Greet brings a heading, emits the form as a raw `@Html` string and links home. On POST it reads the submitted field as `r.who`, an ordinary payload field.
- Router emits @Render and is declared after the page shards, so @Render queues behind every fragment. ShardView Page appends each `h.markup` to `var html` and answers @Response when @Render arrives.
- `if not (html == "")`: no fragments means no response, and the server turns that into a 404. There is no `!=` in the language.
- Live: `veinc serve samples/web_site.vein --port 8080`, open http://localhost:8080/, click 'say hello', submit `Ada` and get 'Hello Ada', then try /nope for the 404.

## Lesson 7. No try/catch: failure is a message ★

**Goal:** Collect every diagnostic in a program with one `hear`, raise your own with info/warn/error, and see a runtime fault stop only its own block.  
**Length:** about 3 min  
**Samples:** `samples/diagnostics.vein`

**Open with:** I'm going to divide by zero on purpose, and the program keeps going.

### Say

- Collector is the catch: `hear *Vein.Diagnostics.Report.@DiagnosticRaised as d`. `d.severity` is an int (0 info, 1 warning, 2 error), and Collector prints each with its own prefix: note, WARN, ERROR.
- A catch belongs to the code that failed, but a `hear` belongs to whoever cares. Collector gets every diagnostic in the program, and no failing shard knows it exists.
- Validate brings a row with an empty title and rank -1, then calls `*Vein.Diagnostics.Report.info`, `warn` and `error`. Nothing failed here: the program made a judgement and reported it.
- Compute evaluates `5 % 0`, a remainder by zero, and the runtime raises the same event: `ERROR | Compute (once): Attempted to divide by zero.` It names the shard and the phase.
- The block stops, not just the statement: 'THIS LINE NEVER PRINTS' never prints. Carry_on still runs in `settled` and prints '-- the program is still alive --' and both rows.
- The collected lines appear after the plain prints because Collector answers with another @Print, which joins the back of the same queue.

### Show — `samples/diagnostics.vein` lines 50–58
The catch: one hear for every diagnostic in the program

```vein
shard Collector {
    hear *Vein.Diagnostics.Report.@DiagnosticRaised as d {
        // severity is an int, not an enum: 0 info / 1 warning / 2 error. stdlib/Diagnostics.vein
        // says why — a cross-bundle enum needs link-time support that does not exist yet.
        if d.severity == 0 { emit *Vein.Console.Io.@Print { text: "   note  | " + d.message } }
        if d.severity == 1 { emit *Vein.Console.Io.@Print { text: "   WARN  | " + d.message } }
        if d.severity == 2 { emit *Vein.Console.Io.@Print { text: "   ERROR | " + d.message } }
    }
}
```

### Show — `samples/diagnostics.vein` lines 62–75

### Show — `samples/diagnostics.vein` lines 79–108
A real fault stops its block; the rest of the program carries on

```vein
shard Compute {
    run once {
        emit *Vein.Console.Io.@Print { text: "-- dividing --" }
        emit *Vein.Console.Io.@Print { text: "   5 % 2 = " + (5 % 2) }

        // `% 0` genuinely throws, and this is the whole demonstration:
        //
        //   * the line below does not print — the BLOCK stops, not the statement. Resuming
        //     mid-block would leave the world in a state no source line describes.
        //   * the message names the shard AND the phase (`Compute (once)`), because "something
        //     threw" is useless and "which unit of work died" is not.
        //   * shard Carry_on below still runs. One broken unit does not take the program.
        emit *Vein.Console.Io.@Print { text: "   5 % 0 = " + (5 % 0) }
        emit *Vein.Console.Io.@Print { text: "   THIS LINE NEVER PRINTS" }
    }
}

// `settled`, not `run once`, and the difference is load-bearing: the rows are brought in Validate's
// `run once`, and a `bring` commits at the END of its phase (docs/RULES.md 12b). A `target` in
// another `run once` block would run BEFORE that commit and print nothing at all — which looks
// exactly like "the fault destroyed the rows" and is nothing of the kind. Written the wrong way
// first, and the empty output is what caught it.
shard Carry_on {
    settled {
        emit *Vein.Console.Io.@Print { text: "-- the program is still alive --" }
        target $Row #Row as r {
            emit *Vein.Console.Io.@Print { text: "   row: [" + r.Row.title + "] rank " + r.Row.rank }
        }
    }
}
```

`veinc run samples/diagnostics.vein --ticks 1`

Real output:

```text
   note  | 2 rows to check
   WARN  | a row has an empty title

   row: [write the docs] rank 3
```

### Watch out

- Don't repeat the header's 'the same six lines still appear'. This run prints four diagnostic lines: three raised and one fault.
- Carry_on is in `settled` because the rows brought in Validate's `run once` commit at the end of that phase. Another `run once` block would see nothing (RULES 12b).
- emit queues, so the Collector's lines arrive one hop after an inline @Print (RULES 21).
- Validate reports but does not reject. Both rows still exist and are printed.
- A file or network failure is a message too: @FileMissing, @Failed, @Undelivered (RULES 28b).

## Lesson 9. Four loops, and no `for`

**Goal:** Pick the right loop (`while`, `repeat N as i`, `target <list> as x`, `target $Shape #Mark as e`) and use `break` and `continue` in all four.  
**Length:** about 4 min  
**Samples:** `samples/loops.vein`

**Open with:** There's no `for` and no `in` in VeinScript. There are four loops instead, and each one says what it's walking.

### Say

- `while i < 10` with `continue` at 2 and `break` at 5 prints 1, 3, 4.
- `repeat 3 as r` counts from 0, and `r` is the same number the built-in `Index` gives: 'repeat r=0 Index=0'.
- A count is a limit, not a promise: `break` at `r == 2` stops `repeat 10` after 'capped r=0' and 'capped r=1'.
- `words("alpha beta skip gamma")` returns a list and `target … as w` walks it. `continue` skips "skip", so three words are numbered.
- The fourth loop is the identity loop in Report: `target $Score #Player as p` with the same `continue`. Make brings Ada 30, Grace 20 and Alan 10, and Alan's 10 points never print.
- Report runs in `each tick`, not in Make's `run once`, because a bring commits at the phase boundary. With `--ticks 2` the two score lines print twice.

### Show — `samples/loops.vein` lines 32–57

```vein

    emit *Vein.Console.Io.@Print { text: "while i=" + i }

    emit *Vein.Console.Io.@Print { text: "capped r=" + r }

// A loop over a LIST. Same statement, same two words.
```

## Lesson 10. A state machine with `enum` and `match`

**Goal:** Declare an enum inside the shape that owns it, advance it by comparing cases, and read it back with `match … when … else`.  
**Length:** about 3 min  
**Samples:** `samples/enum_state.vein`

**Open with:** An enum in VeinScript lives inside the data it describes. There's no top-level enum at all.

### Say

- `enum State { Kickoff, Play, Over }` is declared inside `shape $Match`, and `state: State` types the field.
- `bring Referee(State.Kickoff, 0)`: a case is a value you can pass around, bound by position (state, then clock).
- Each tick, Whistle bumps the clock, moves Kickoff to Play, and moves Play to Over once `m.Match.clock >= 3`. Logic is written in words, like `and`.
- Commentary reads the state back in `settled` with `match m.Match.state { when Kickoff … when Play … when Over … else … }`.
- The output is t1 in play, t2 in play, t3 full time, t4 full time. 'awaiting kickoff' never prints because Whistle moved on in frame 1 before settled ran, and 'NO STATE' never prints either. That absence is the check.

### Show — `samples/enum_state.vein` lines 27–64
An enum inside its shape, advanced each tick, read back with match

```vein
shape $Match {
    enum State { Kickoff, Play, Over }
    state: State
    clock: int
}
mark #Match

builder Referee { $Match   mark #Match }

shard Boot { run once { bring Referee(State.Kickoff, 0) } }

// The referee. Each frame it advances the clock and decides what state the match is in — and it
// decides by COMPARING CASES, which is the thing that could not be written.
shard Whistle {
    each tick {
        target $Match #Match as m {
            m.Match.clock = m.Match.clock + 1

            if m.Match.state == State.Kickoff { m.Match.state = State.Play }
            if m.Match.state == State.Play and m.Match.clock >= 3 { m.Match.state = State.Over }
        }
    }
}

// …and reading it back by `match`, which is the other half. An `else` arm would have caught every
// frame before this worked, so its absence from the output is the assertion.
shard Commentary {
    settled {
        target $Match #Match as m {
            match m.Match.state {
                when Kickoff { emit *Vein.Console.Io.@Print { text: "t" + m.Match.clock + " awaiting kickoff" } }
                when Play    { emit *Vein.Console.Io.@Print { text: "t" + m.Match.clock + " in play" } }
                when Over    { emit *Vein.Console.Io.@Print { text: "t" + m.Match.clock + " full time" } }
```

## Lesson 11. `$Enemy` and `#Enemy`: marks are tags that stay

**Goal:** Declare marks, combine several in a query, swap them at runtime, and know that declaring marks turns on name checking.  
**Length:** about 4 min  
**Samples:** `samples/entities_marks.vein`

**Open with:** This file gives a shape and a mark the exact same name, on purpose.

### Say

## Lesson 12. One word, four sigils

**Goal:** Read `$`, `#`, `@` and the bare builder name as part of a name, and see `$Switch`, `#Switch`, `@Switch` and `Switch` coexist.  
**Length:** about 3 min  
**Samples:** `samples/sigil_names.vein`

**Open with:** This file declares `Switch` four times, and none of them collide.

### Say

- `shape $Switch` is data, `mark #Switch` is a tag, `event @Switch` is a message, and `builder Switch` is the template. Inside its own bundle a builder is normally written bare, as in `bring Switch(1)`. Its sigil `&` shows up in a qualified path, as in `bring *Vein.Console.Io.&Console(…)`, and when you name it to a tool: `veinc scaffold samples/sigil_names.vein '&Switch'` prints the bring call, while a bare `Switch` there gives the `@Switch` emit body.
- `builder Switch { $Switch   mark #Switch }` uses the word three times and means something different each time.
- `bring Switch(1)` and `bring Switch(0)` spawn two identities with `on` set to 1 and 0.
- In `settled`, Flip targets `$Switch #Switch as s` and emits `@Switch { n: s.Switch.on }`. Listen hears `@Switch as e` and prints `e.n`.
- Output order: '$Switch #Switch matched 2' prints before the two '@Switch says' lines even though Flip runs first. Report queues its @Print straight from `settled`, while each @Switch line needs one more hop: Flip's @Switch is queued, Listen hears it, and only then queues its @Print, behind Report's.

## Lesson 14. `target … by` and `Index`: order and position

**Goal:** Sort a query at read time with `by Shape.field` (ascending, stable, ordinal), and number, cut off and stripe rows with `Index`.  
**Length:** about 4 min  
**Samples:** `samples/entities_ordered.vein`, `samples/entities_index.vein`

**Open with:** Five rows, brought in scrambled order. The same rows print in three different orders in one frame, and not one id moves.

### Say

- Seed brings delta 4, alpha 1, Zeta -2, charlie 3, bravo 1, and a plain `target $Row #Row` yields exactly that spawn order.
- `target $Row #Row by Row.rank as r` sorts when the rows are read, so -2 Zeta comes first. Ints sort numerically, and `by` comes before `as`.
- `by Row.title` compares strings ordinally, so capital 'Zeta' comes before every lowercase name. The sort is stable: alpha and bravo both have rank 1 and keep spawn order.
- `Entity` says which identity, and `Index` says which iteration, starting at 0. In entities_index.vein, `(Index + 1) + ". "` numbers six rows from 1 with no counter variable.
- `if Index < 3` is a top-three cutoff, `Index % 2 == 0` stripes (0 alpha, 2 gamma, 4 epsilon), and `Index == 0` finds the first row.
- `Index` counts position in the order the loop already yields. It never sorts. If you run `veinc run samples/entities_index.vein --ticks 1` after the main run, crop it after 'first is alpha': its last section prints three rows under '-- first two of the wide ones --' (see Watch out).

## Lesson 15. Defaults, `base` and `?`

**Goal:** Put defaults on shape fields, order includes so the optional fields trail, and use `base` and `?` at the call site.  
**Length:** about 4 min  
**Samples:** `samples/builder_defaults.vein`

**Open with:** One argument builds a complete panel with seven fields, and the rule that allows it also decides how you lay out your shapes.

### Say

- `builder Panel { $Content $Style $Layout   mark #Panel }` flattens to title, body, class, accent, padded, column, order. Include order is parameter order.
- Only `title` has no default, so `bring Panel("Welcome")` is a complete call and prints 'Welcome' then '(no description yet)'.
- There are no named arguments. To change `accent` you fill every slot before it, and `base` means 'the declared default here': `bring Panel("Danger", base, "panel warn", "#aa4444")`.
- `base` fills a slot but does not skip it: `bring Panel("Footer", base, base, base, false, 1, 9)` still passes seven arguments, and its `order` of 9 is why Footer prints last.
- The `"salu"` call is the output of `veinc scaffold samples/builder_defaults.vein '&Panel'` pasted in, with the REQUIRED title's `base` replaced by "salu". There is one slot per line, each labelled with its type, its shape and whether it's required, and a comma after every slot but the last.
- `?` is the other tool: `bring Draft("Untitled", ?)` knowingly leaves `note` empty and still honours `slug`'s default. The output shows note=[] slug=[untitled].

## Lesson 16. Variants with `from`

**Goal:** Derive a builder from another with `from`, fixing parameters by name and adding marks.  
**Length:** about 3 min  
**Samples:** `samples/builder_variants.vein`

**Open with:** A big coin is a coin worth five. Say that once, not at every call site.

### Say

- Coin includes `$Position` and `$Prize`, so it takes five parameters (x, y, z, value, sound) and carries `mark #Coin`.
- `builder BigCoin from Coin { value = 5 }` fixes `value` by name, so BigCoin takes four arguments.
- `builder GoldCoin from BigCoin { sound = "gold.wav"   mark #Shiny }` chains: it inherits value = 5, fixes sound, and adds a mark, leaving three arguments.

- Parameters are fixed by name, never by position, so a shape added to Coin reaches every variant.

## Lesson 18. Two forces, one velocity

**Goal:** Use stdlib shapes through qualified builder includes, watch a constant per-tick force build up into acceleration, and see the step lag one frame behind.  
**Length:** about 4 min  
**Samples:** `samples/motion.vein`

**Open with:** Gravity and wind don't know about each other. Every frame both push the same velocity, one on y and one on x, and the object falls faster and faster along a straight slant.

### Say

- Mover includes `*Vein.Transform.Spatial.$Position` and `*Vein.Transform.Spatial.$Velocity`: `bring Mover(0.0, 100.0, 0.0,  0.0, 0.0, 0.0)` gives position first, then velocity.
- Ticker carries Vein.Time's `$Clock`, and `bring Ticker(0.0, 0.5)` sets `now` to 0 and `delta` to 0.5.
- Gravity does `m.Velocity.y -= 4.9` and Wind does `m.Velocity.x += 1.0`. The stdlib declares every axis of `$Velocity` with `folds sum`, which is what lets two forces on the same axis both land. Here they push different axes, so each write would land even without folds.
- Velocity keeps its value from tick to tick, so adding the same force every tick makes it grow, and a constant force becomes acceleration: v goes '1, -4.9', then '2, -9.8', then '3, -14.7'.
- Step moves by velocity * 0.5, yet frame 1 prints 'at 0, 100'. Step reads the velocity as it stood at the end of the previous frame, which is an explicit Euler step.
- The standard library ships shapes, not behaviour, so integrating position is the app's own Step shard. Live: step it in the Workbench Runtime panel and watch Position and Velocity change tick by tick.

### Show — `samples/motion.vein` lines 71–97

```vein

    each tick { target $Velocity #Moving as m { m.Velocity.y -= 4.9 } }
}

shard Wind {
    each tick { target $Velocity #Moving as m { m.Velocity.x += 1.0 } }
}

shard Clock {
    each tick { target $Clock #Clock as c { c.Clock.now += c.Clock.delta } }
}

// ---- the application's own integration step ----------------------------------------------------
//
// THE FIRST FRAME DOES NOT MOVE, and that is the phase boundary showing through rather than a bug.
// The forces above contribute during frame 1; those contributions are reconciled at the boundary
// and are what frame 2 reads (RULES 11/12b). So position always steps by the velocity as it stood
// at the END of the previous frame — an explicit Euler step, which is the ordinary one.

shard Step {
    each tick {
        target $Position $Velocity #Moving as m {
            m.Position.x += m.Velocity.x * 0.5
            m.Position.y += m.Velocity.y * 0.5
        }
    }
}
```

## Lesson 20. A page by hand: fragments, a Kernel and a view

**Goal:** Build the request → fragments → ShardView → response pipeline by hand, and see that declaration order is queue order.  
**Length:** about 3 min  
**Samples:** `samples/site.vein`

**Open with:** No function returns this web page. Two shards shout pieces of it, and a view stitches them together. Move one shard and the page goes blank.

### Say

- `publicator SiteApi` declares the four events itself: `@Request`, `@Html`, `@Render` and `@Response`, each with a `shared("…")` label.
- Header and Body both `hear @Request as req` and each emits its own `@Html { markup: … }` fragment. Nobody calls them.
- Kernel also hears `@Request` and emits `@Render`. It's declared after the content shards, so its event queues behind their fragments.
- `ShardView Page` keeps `var html: string`, appends every fragment with `html += f.markup`, and emits `@Response` with status 200 when `@Render` arrives.
- `veinc render samples/site.vein /` fires one request with no socket. The trace shows Header, Body, Kernel, then Page, followed by `HTTP 200` and the page, and it names the event `@local.Site.Html`.
- Live: move shard Kernel above Header and render again. You get HTTP 200 with `<html><body></body></html>`, because @Render was queued first.

### Show — `samples/site.vein` lines 24–53
Content shards, a Kernel, and the ShardView that assembles them

```vein
shard Header {
    hear @Request as req { emit @Html { markup: "<h1>VeinScript</h1>" } }
}

shard Body {
    hear @Request as req {
        emit @Html { markup: "<p>Reactive page, assembled from fragments.</p>" }
    }
}

// Kernel closes the request phase (declared last, so @Render is queued after the fragments).
shard Kernel {
    hear @Request as req { emit @Render { } }
}

// The ShardView: tons of `hear`, concatenating HTML (and JS) into one page, then rendering.
ShardView Page {
    var html: string

    hear @Html as f {
        html += f.markup
    }

    hear @Render as r {
        emit @Response {
            status: 200
            body: "<html><body>" + html + "</body></html>"
        }
    }
}
```

## Lesson 24. One program, many windows: broadcast and roles

**Goal:** Spawn named consoles, send to one, a random one or all of them on a timer, and give each window its own role with `match here()`.  
**Length:** about 7 min  
**Samples:** `samples/console_broadcast.vein`, `samples/console_roles.vein`

**Open with:** One command, four windows, and every two seconds the first one talks to the other three.

### Say

- Opening a window is just an event: `emit *Vein.Console.Io.@Console { name: #Alpha, firsttext: … }`. The name is a mark, and it becomes that window's address.
- `every 2 { … }` is a wall-clock timer, and `var n: int` is state that belongs to this shard and survives between rounds.
- Each spawned window re-runs this same program, so `if here() == #Main` keeps the broadcasting in the window you launched.
- Three ways to address: a fixed mark with `to: #Alpha`, a random one with `pick(consoles)`, and everybody with `target consoles as c` over a plain list. Inbox runs in every window and prints `m.from + ": " + m.text` for each line it receives. Only Alpha, Beta and Gamma are sent anything, so Main stays quiet after its opening line.
- Live: run it and tile the windows. Every round Alpha gets its own line plus the broadcast, and one random window also gets 'you were picked'.
- console_roles.vein generalises `if here()` into a role switch: Worker's `match here()` has Alpha echo to `#Main`, Gamma relay to `#Alpha`, and Beta count with `var seen: int`.
- The `else` arm covers Main, which has no `when` of its own and prints the replies. Live: run `veinc run samples/console_roles.vein`, close Beta's window, and Main reports it as not running via `@Undelivered`.

## Lesson 25. HTTP as a request and a reply

**Goal:** Call an HTTP service with `@Fetch`, and handle `@Fetched` and `@Failed` separately.  
**Length:** about 3 min  
**Samples:** `samples/net_fetch.vein`

**Open with:** A web request with no await, no callback and no promise: one event goes out, one event comes back. And a 404 is not a failure here.

### Say

- Boot emits `*Vein.Net.Http.@Fetch { url, method, body }` for httpbin's `/ip` once, and Poller emits another for `/uuid` every 5 seconds.
- Results hears `@Fetched` and prints `r.status + " " + r.url`, then the body.
- A 404 or 500 still arrives as `@Fetched`, because the server answered. `@Failed` means no answer at all (bad host, refused connection, timeout) and carries `f.reason`.
- The request runs off the event loop and posts its result back, so `every 5` keeps firing while a slow host hangs.
- Live: run it, watch the IP reply and then a fresh UUID every 5 seconds, and end with Ctrl+Z and Enter.

## Lesson 26. Peers: `@Listen`, `@Link` and a signed `audience`

**Goal:** Connect two programs over TCP with a shared key, and filter whose messages are heard.  
**Length:** about 4 min  
**Samples:** `samples/net_peer.vein`, `samples/net_spoke.vein`

**Open with:** The hub is never told where the spoke lives, and it still answers every ping.

### Say

- The hub emits `*Vein.Net.Peer.@Listen { as: #Hub, at: 9700, key: "shared-secret" }`: `as` is who this program is on the network.
- The spoke listens as `#Spoke` on 9701, then `@Link { name: #Hub, at: "127.0.0.1:9700", … }`. Linking registers a route and connects nothing.
- Pinger sends `@Send { to: #Hub, text: "ping " + round }` every 2 seconds, the same shape as a console send.
- Frames are signed with the key, so the hub's `hear … audience #Spoke` is a real barrier, not a request. Inbox, with no audience, still sees every message.
- Trusted replies with `@Send { to: m.from, … }` to a peer it never linked. It learned the route from the signed frame.
- Live: start the spoke first, and each ping comes back as @Undelivered. Then start the hub in a second terminal, and the spoke prints 'Hub replied: ack ping N'. A mark used as a value is its bare name, so there is no `#`.

### Show — `samples/net_peer.vein` lines 27–54
The hub: listen, a trusted handler, an inbox

```vein

    run once {
        // `as` is who this program IS on the network. Without it every peer in the world would
        // answer to #Main — harmless for one machine's pipes, useless across a network.
        emit *Vein.Net.Peer.@Listen { as: #Hub, at: 9700, key: "shared-secret" }
        emit *Vein.Console.Io.@Print { text: "hub listening on 9700 as #Hub — waiting for #Spoke" }
    }
}

// `audience #Spoke` is the whole reason the key exists. It admits the spoke and refuses everyone
// else — and because the frame was signed, "refuses" is a guarantee, not a convention politely
// honoured by well-behaved peers.
shard Trusted {
    hear *Vein.Net.Peer.@Message as m audience #Spoke {
        emit *Vein.Console.Io.@Print { text: "trusted " + m.from + ": " + m.text }
        // Replying to a peer that was never linked — the route was learned when it spoke.
        emit *Vein.Net.Peer.@Send { to: m.from, text: "ack " + m.text }
    }
}

// Anything from someone OTHER than the spoke still lands here: the barrier filters one handler, it
// does not discard the message. That is what you want — unexpected is not the same as unwelcome,
// and a program that cannot see strangers cannot report them either.
shard Inbox {
    hear *Vein.Net.Peer.@Message as m {
        emit *Vein.Console.Io.@Print { text: "  (inbox saw " + m.from + ")" }
    }
}
```

## Lesson 27. A networked chat in two files

**Goal:** Run a TCP chat where the server keeps its roster as entities and relays each line to everyone except the sender.  
**Length:** about 6 min  
**Samples:** `samples/chat`

**Open with:** Laptop on the left, laptop on the right, one server, and not one line of socket code. The server doesn't know a single address in advance.

### Say

- The server emits `*Vein.Net.Peer.@Listen { as: #Server, at: 9700, key: "chat-secret" }` once and never links a client.
- The roster is made of entities: a newcomer becomes `spawn()` plus `attach $Client` with `addr: m.from`, and `target $Client` is how the server looks through it. `var known: bool` carries the answer out of the loop.
- The relay skips the sender with `if not (self.Client.addr == m.from)`, because there is no `!=`.
- On the client, `let first = not joined` snapshots the state. The first line you type is your name, and `@Listen { as: i.text, at: 0, … }` makes it your network identity, with the OS picking the port.
- `@Link { name: #Server, at: ServerAddress(), … }` registers the route, sending "is here" puts you on the roster, and `audience #Server` on Incoming admits only the server's frames.
- Live: start the server (it prints 'server listening on 9700'), then a client in each of two more terminals or machines. Type `bob` in one and `alice` in the other, then `hi bob`.
- The server prints '* bob joined' and 'alice: hi bob'. Bob sees alice's lines, and alice never gets her own line back.

### Show — `samples/chat/server.vein` lines 24–59
The server: listen, keep a roster of entities, relay

```vein
shard Boot {
    run once {
        emit *Vein.Net.Peer.@Listen { as: #Server, at: 9700, key: "chat-secret" }
        emit *Vein.Console.Io.@Print { text: "server listening on 9700 — waiting for clients" }
    }
}

shard Relay {
    var known: bool

    hear *Vein.Net.Peer.@Message as m {
        // 1. Do we already have this sender? `target` is the only way to look through the roster,
        //    so the answer comes back on shard state rather than as a return value.
        known = false
        target $Client as self {
            if self.Client.addr == m.from { known = true }
        }

        // 2. A newcomer becomes an entity. That is the whole "stacking" mechanism.
        if not known {
            let e = spawn()
            attach $Client to e { addr: m.from }
            emit *Vein.Console.Io.@Print { text: "* " + m.from + " joined" }
        }

        emit *Vein.Console.Io.@Print { text: m.from + ": " + m.text }

        // 3. Relay to everyone except the sender. No `!=` in VeinScript (LANGUAGE.md §7) —
        //    inequality is `not (a == b)`. Without the guard the sender gets their own line back.
        target $Client as self {
            if not (self.Client.addr == m.from) {
                emit *Vein.Net.Peer.@Send { to: self.Client.addr, text: m.from + ": " + m.text }
            }
        }
    }
}
```

## Lesson 28. JSON in, identities, JSON out

**Goal:** Parse JSON with `fromJson`, bring one identity per record in sorted order with `ordered by`, and serialise a shape back with `toJson`.  
**Length:** about 4 min  
**Samples:** `samples/json_roundtrip.vein`

**Open with:** A string arrives, becomes a world you can query, and each record goes back out as JSON with its types intact.

### Say

- `fromJson(payload)` turns the string into plain data: objects become dictionaries and arrays become lists, so `doc.rows` is ordinary field access and `len(doc.rows)` prints 3.
- The payload is four one-line string literals joined by `+`: each of the first three lines ends with a trailing `+`, which keeps the expression open (RULES 1, 3).
- `target doc.rows as row: $Row` is an ascription: it declares what the outside data looks like, and fields are read directly as `row.title`. Today the compiler checks only that `$Row` exists (VS0233). A misspelt field such as `row.titel` still compiles and reads as empty.
- `ordered by rank { … }` sorts the brings themselves. The payload arrived as 4, 1, -2, but the rows are spawned -2, 1, 4, so the plain query without `by` prints them in rank order.
- `toJson(r.Row)` serialises the `$Row` shape on the identity in declaration order, for example {"title":"Zeta","rank":-2,"done":false}. Ints stay ints and bools stay bools.

### Watch out

- `toJson` takes a shape (`r.Row`), never the entity, because nothing can ask an entity which shapes it carries (RULES 14, 24b).
- Ascribed rows read `row.title`, while a component query reads `r.Row.title` (RULES 27).
- This is interpreter-only: `veinc emit` still prints the C# (to stdout, or into a folder with `-o`), but it also prints a note for each of fromJson() and toJson() saying it has no C# emission, so this file will not compile (RULES 24b).
- Malformed JSON parses to null, not a crash (RULES 24b).
- `ordered by` reorders only `bring`, and every key is evaluated first (RULES 14d, 14e). The report is in `settled`, so run with `--ticks 1` or more.

## Lesson 29. Files are events: route them by tag

**Goal:** Write and read files through events, tag each request, and route every reply through one checked `match f.tag`.  
**Length:** about 5 min  
**Samples:** `samples/file_tags.vein`

**Open with:** Five files, one handler, and not one path spelled twice.

### Say

- There's no open, close or handle: `@WriteFile` answers `@FileWritten`, `@ReadFile` answers `@FileLoaded`, and either one answers `@FileMissing` when it fails.
- Seed writes five files, and each write carries a `tag`: `#Config`, `#Log`, and a computed `"slot" + (i + 1)` for three saves.
- Ask hears every `@FileWritten` and reads the file back with `tag: w.tag`. The runtime hands the tag back untouched.
- Route's `match f.tag` has `when #Config` and `when #Log` arms. A mark in value position evaluates to its own name, and `when` is checked against the declared marks.
- Computed tags can't be named in a `when`, so the slots land in `else`: `bring Slot(slots, trim(f.text)) as s`, then `mark s #Save`.
- The third slot emits `@SavesLoaded`, a new event, so the Report shard that hears it sees all three `#Save` identities. The output ends 'save 1: level=3' to 'save 3: level=9'.
- `@FileMissing` carries the tag too, so its handler routes with its own `match m.tag` and the same `when #Config` / `when #Log` arms. The failure path needs no path comparisons either.

## Lesson 30. A text file becomes identities

**Goal:** Turn a document's lines and words into marked identities, chain phases through events, and query them once they exist.  
**Length:** about 5 min  
**Samples:** `samples/file_words.vein`

**Open with:** `target $Line #Heading` is a sentence about a document.

### Say

- The Parser walks `lines(f.text)`, which strips the line ending whichever it was, and captures `let number = Index + 1` because the inner loop rebinds `Index`.
- Each line becomes an identity: `bring Line(number, line, len(words(line))) as e`.
- A blank line gets `mark e #Blank`, and a line whose first word is exactly `#` gets `mark e #Heading`. The decision is made once and remembered as a mark.
- Inside `target words(line) as w`, each word is brought as a `Word`. The mark goes on `e`, the line from the enclosing loop.
- `emit @Parsed` ends the phase. Nothing brought above is committed yet, so the next event is where the identities exist.
- The report's `target $Line #Heading as l` prints 'heading at line 1: # VeinScript' and 'heading at line 6: # Why identities', then '40 words; longest is 'identities.''.

## The rules that bite (docs/RULES.md)

- **1.** A newline ends a statement, so a continuation must END the line it continues from (a trailing + or a trailing ,). _(first-hour)_
  - wrong: `markup = "<a>" ⏎        + "</a>"`
  - right: `markup = "<a>" + ⏎          "</a>"`
- **2.** There is no != and no ! at all: inequality is not (a == b) and negation is not x (VS0006). Logic is written in words. _(first-hour)_
  - wrong: `a != b`
  - right: `not (a == b)`
- **2b.** } else { goes on ONE line; an else starting its own line is VS0104 (match arms are exempt). _(first-hour)_
  - wrong: `} ⏎ else { … }`
  - right: `} else { … }`
- **3.** A string literal is one line; the escapes are \n \t \r \\ \"; a literal newline inside quotes is VS0003. _(first-hour)_
- **4.** Lexer keywords are reserved in expressions but most are still legal as field names. RULES says 63; the lexer has 62 today, so check the map before choosing a name. _(first-hour)_
  - wrong: `builder Clock { target: string   line = "clock " + target }   // VS0104: the field declaration is fine, reading bare `target` in an expression is not`
- **5.** A builder's OUTPUT FIELD NAME decides what it makes: markup→@Html, css→@Style, code→@Script, line→@Print, a mark member→identity, inherited→what the base builds, none→@BuilderName. _(first-hour)_
- **6.** So markup, css, code and line cannot be parameter names; doing so reports VS0205 at every call site and nothing at the declaration. _(first-hour)_
  - wrong: `builder CodeBlock { code: string … }`
- **7.** A mark member makes a builder an identity template: bring = spawn + attach each shape + mark. _(first-hour)_
  - right: `builder Unit { $Health $Shield   mark #Unit } ⏎ bring Unit(10, 6)`
- **7b.** bring X(…) as name binds the identity a template built; as on a fragment builder is VS0221 and it cannot combine with a count (VS0222).
- **7c.** A variant (builder BigCoin from Coin { value = 5 }) fixes a base's arguments BY NAME and inherits its marks; a cycle is VS0239 and an unknown base is VS0238.
  - right: `builder BigCoin from Coin { value = 5 }`
- **8.** A $Shape include is a compile-time field expansion and bring attaches nothing, so a target on that shape matches zero. _(first-hour)_
  - wrong: `builder Card { $Card   markup = … } ⏎ bring Card("a", "b")            // emits @Html ⏎ target $Card as self { … }      // matches ZERO`
- **9.** Arguments bind positionally across includes in declaration order; ask veinc scaffold <file> '&Name' rather than counting. _(first-hour)_
  - right: `{ $Health $Shield } takes (hp, sp)`
- **10.** spawn() is the only way to make an entity; with no spawn the world is empty and every target matches nothing. _(first-hour)_
- **11.** spawn is immediate; attach, unattach, mark, unmark and destroy are DEFERRED to the commit point after the folds. _(first-hour)_
- **12.** A structural change is invisible inside the event that made it; seed worlds in run once. _(first-hour)_
- **12b.** …but the NEXT event sees it, because commit is per event; run once commits once for all shards, and wiring and rendering cannot see each other within one @Request.
- **12c.** A nested target binds BY NAME, so both the outer and inner bindings are readable in both runtimes.
  - right: `target $Deck as d { target $Card as c { … d.Deck.title … c.Card.face … } }`
- **13.** folds reconciles concurrent writes (two hp -= 1 give hp - 2); only settled sees the reconciled value, so death checks belong there. _(first-hour)_
- **13b.** folds ACCUMULATES across ticks and does not recompute; a child can write its parent's component through a handle (c.Parent.of.Deck.count += 1).
- **13c.** $Parent makes $Position LOCAL and the runtime publishes $World before settled; anything reading world coordinates asks for $World.
- **14.** target binds ONE shape set per loop (several shapes is an AND), and nothing can ask an identity which shapes it carries.
- **14b.** Query order is spawn order unless `by Shape.field` sorts it at read time (stable, strings compared ordinally).
  - right: `target $Row #Row by Row.rank  as r { … }`
- **14c.** Index is the nearest loop's 0-based counter; it counts position in yield order and does NOT sort.
  - right: `bring Item(Index + 1, …)`
- **14d.** ordered by &Builder.$Shape.param { bring … } sorts the BRINGS, which is how fragment output (most of a web page) gets ordered.
  - right: `ordered by &Card.$Card.rank { ⏎     bring Card("delta", 4) ⏎     bring Card("Zeta", -2) ⏎ }`
- **14e.** ordered by also takes a target loop, which is how DATA gets ordered; only bring is reordered.
  - right: `ordered by rank { ⏎     target doc.rows as row { ⏎         if row.rank > 0 { bring Row(row.title, row.rank) } ⏎     } ⏎ }`
- **15.** $Enemy and #Enemy are different things: a different keyword and a different sigil, and a program may use both. _(first-hour)_
- **15b.** Components unify by bare name across bundles, and a shape cannot include a shape (VS0007); a field mismatch is VS0220 or VS0332.
- **15c.** A shape may BRING marks, which arrive and leave with it in the same commit.
  - right: `shape $GameCamera { zoom: float, #CameraFollow }`
- **16.** A mark is just a name unless declared; a bundle that declares any mark has its mark names checked (VS0218).
  - right: `mark #Enemy`
- **17.** Only shared("…") inside a publicator crosses a bundle boundary; everything else is bundle-private.
- **17b.** The qualified *A.B.P.$Shape / #Mark form is for INCLUDES and DISCOVERY; target, mark, audience and match take a bare name.
- **17c.** An IMPORTED $Shape becomes a real component once something attaches it; target it by its bare name.
  - right: `builder Conn { *Vein.Rest.Db.$Connection  mark #Conn }`
- **17d.** The shared("…") string is a LABEL shown in the completion row; over 160 characters is the VS0243 warning.
- **18.** need "Author.Bundle" names a dependency, widens bare names (lookup order: local → built-in → need) and LINKS the bundle; use is VS0338, a missing author is VS0339 and an unknown bundle is VS0340. _(first-hour)_
  - wrong: `use Console`
  - right: `need "Vein.Console"`
- **18b.** need "Author.Bundle" as Y imports QUALIFIED only (*Y.…) and widens nothing; this is the answer to a VS0216 ambiguity.
  - right: `need "Vein.Math" as M   →   *M.Roots.sqrt(16.0)`
- **19.** A bundle can span files (publicators/*.vein for API, shards/*.vein for behaviour); fragments merge BEFORE the main file, and an API declaration in a fragment is VS0321.
- **20.** An event is Author.Bundle.Name while a shape is just its name; runtime and stdlib events (@Request, @Print, @Ticked) keep bare names.
- **20b.** An SF runs INLINE (its brings land where you called it); a shard hearing an event does not.
- **21.** bring and emit QUEUE, they do not write; the queue drains only after every handler of the current event has finished.
- **22.** veinc serve gives every request a fresh interpreter, so run once re-runs per request; veinc render is the same pipeline, one-shot.
- **23.** Under Git Bash, pass MSYS_NO_PATHCONV=1 for a / argument, or the path becomes C:/Program Files/Git/. _(first-hour)_
  - wrong: `veinc render f.vein /`
  - right: `MSYS_NO_PATHCONV=1 veinc render f.vein /`
- **24.** There are four checks guarding different things: dotnet test (behaviour), check-ir.sh (IR shape), check-backend.sh (backend meaning), check-perf.sh (speed).
- **24b.** JSON crosses the boundary with fromJson(text) and toJson(shape); integral numbers parse as int, malformed input is null, and both are interpreter-only.
  - right: `toJson(r.Row)`
- **25.** When measuring the backend, use Release on both sides and measure past JIT warm-up.
- **26.** Arity and literal types are checked (VS0204, VS0228, VS0227, VS0229, VS0230); nothing else about a value is, and a missing value reads as empty, not zero. _(first-hour)_
  - wrong: `bring Row(42, "words")`
- **27.** target rows as row: $Row declares what OUTSIDE data looks like, so fields are checked and read directly (row.title); an unknown shape is VS0233.
  - right: `target rows as row: $Task { bring Task(row.id, row.title, row.rank, row.done) }`
- **28.** A character is a one-character string: no char type and no 'a' literal; two strings compare ordinally.
  - right: `fn isDigit(c: string) return bool { return c >= "0" and c <= "9" }`
- **28a.** Splitting is done by the host: split keeps empties, lines strips \r, words drops empties, plus chars and trim; all return lists.
  - wrong: `split(text, "\n")   // leaves \r on CRLF lines`
  - right: `lines(text)`
- **28d.** Conversions are named after the type (int, float, string, bool) and are total (int("abc") is 0); guard with isNumber.
  - right: `if isNumber(typed) { let n = int(typed) } else { … }`
- **28e.** Ordering decides in three steps: both text → ordinal; both numeric (parsed text included) → numeric; otherwise ordinal on text, never silently zero.
- **28b.** A file is an event and a failure is a message: @ReadFile answers @FileLoaded or @FileMissing, and there is no catch.
  - right: `emit *Vein.Files.Io.@ReadFile { path: settings, tag: #Config }`
- **28c.** Route file events by tag, not by path; a tag is a mark checked in when arms, so a typo is caught at compile time as a VS0218 warning (in a bundle that declares its marks).
  - right: `hear *Vein.Files.Io.@FileLoaded as f { ⏎     match f.tag { ⏎         when #Config { … } ⏎         else         { … } ⏎     } ⏎ }`

## What VeinScript deliberately does not have (docs/SYNTAX-DECISIONS.md)

| id | not in VeinScript | write instead | why |
|---|---|---|---|
| D1 | C-style typed parameters such as `int v` (and mixed `hp : int` / `int v`) | `name: Type` everywhere: `fn clamp(v: int, lo: int, hi: int) return int`, `let x: T = …` | One rule that reads left to right. Leaving out `: Type` is then naturally just `let x = …`. |
| D2 | `when cond { … }` as a general conditional | `if` / `else if` / `else`. `when` is only the arm keyword inside `match`. | Identity comes from shape/shard/target, not from renaming conditionals. `when` is kept for match arms. |
| D3 | `for`, `in`, `loop` | `target coll as x { … }` for any collection or query, `repeat N [as i] { … }` for counting, `while cond { … }`, plus break/continue | `target` unifies iterating data with querying identities, which is the central IOP verb. The language reads as targeting sets rather than running C-style loops. |
| D4 | `push` (a field-write keyword) | Compound assignment (`self.Health.hp -= 1`). When several shards write one field, the shape declares a reducer: `hp: int folds sum`. | It separates the per-shard write from the merge policy, which is declared once on the data. The result is deterministic and independent of shard order. |
| D5 | `class` | Data in `shape` (component), `type` (plain value) and `event` (message). All behaviour in `shard`. | The data/behaviour split is what makes folds, deterministic scheduling and parallelism possible. Web and desktop are modelled as identities + shards too. |
| D6 | A function that both emits and returns, or an `SF` with a return value | `fn f(…) return T { return … }` for values; `SF f(…) { emit … }` for named emit sequences (`-> T` on an SF is VS0105, `return` outside an fn is VS0107) | 'Returns a value' versus 'emits events' can be decided from the declaration alone. Purity cannot be checked, so a 'verified pure' promise could not be kept. |
| D7 | Semicolons | A newline ends a statement (a virtual terminator). To continue an expression, end the line with an operator or comma. | The lexer's newline terminator (CanEndStatement) was kept, and blocks use braces. |
| D8 | The `::` scope operator (`::Health.hp`, `M::x`) | `self.Health.hp` (name the target binding) and `*Author.Bundle.Publicator.member` for cross-bundle references | `::` carried two unrelated meanings, and both already had a better spelling. `M::x` had zero uses in samples/ and stdlib/. |
| D9 | List mutation: append, sort in place, push | Build lists with `[a, b, c]` or with split/lines/words/chars. Use `len`, `xs[i]`, `target xs as x`, `pick`, `join`. Order with `ordered by` or `target … by`. | Lists exist as values you can build, index, measure and iterate. Mutation has not been designed yet. |
| D10 | User-defined generics | Built-in collections only | Deferred and low priority. Built-ins are special-cased in v1. |
| D11 | Top-level `enum` declarations | Declare the enum inside the shape that owns it: `shape $Match { enum State { Kickoff, Play, Over }  state: State }` (top level is VS0102) | State definitions stay next to the data they constrain, with no floating global enum namespace. Meaning attaches to identities. |
| D12 | `!` and `!=` | `not x` and `not (a == b)`. The parentheses matter: `not x == y` is `(not x) == y`, and VS0008 warns about it. | and/or/not are already words, so a symbolic exception would be inconsistent. A dropped `!` flips a condition and still compiles. This is also the general rule: 'C does it' is not an argument. |
| D13 | Descending order and sorting by more than one component field | `target $Row #Row by Row.rank as r { … }`: ascending, stable, strings compared ordinally | Sorting at read time keeps entity ids stable, so references to rows are never disturbed. Only ascending order on one field has been built. |

## Glossary

| term | syntax | meaning | first seen in |
|---|---|---|---|
| Identity Oriented Programming (IOP) | `shape · mark · event · shard · target` | The paradigm. A program is a set of identities that carry data and tags. All behaviour lives in shards, which target matching identities. There is no class, and shards never call each other. | `samples/demo.vein` |
| Identity / Entity | `let e = spawn()  ·  Entity` | Something in the world: an id that shapes and marks hang off. `Entity` is also a keyword. As a type it is an entity id. As an expression it is the id of the nearest target binding, or 0 outside a target. | `samples/entities.vein` |
| spawn() | `let e = spawn()` | A built-in call, not a keyword. It creates an identity immediately and is the only way to make one. With no spawn the world is empty and every target matches nothing. | `samples/entities.vein` |
| Shape | `shape $Health { hp: int folds sum }  ·  $Health` | A named group of fields an identity carries (a component). Across bundles, shapes with the same bare name are the same component. A shape can declare an enum and can bring marks with it. | `samples/entities.vein` |
| Mark | `#Enemy  ·  mark e #Enemy  ·  unmark self #Enemy  ·  mark #Enemy (declaration)` | A tag with no fields that an identity wears. Declaring any mark at bundle level turns on VS0218 checking for that bundle. Used as a value, a mark evaluates to its own name, which is how console addresses and file tags work. | `samples/entities.vein` |
| Event | `event @Hit { amount: int = 1 }` | A message type. A field with `=` is optional and one without is required. Since the last commits, an event's identity is Author.Bundle.Name, while a shape's is just its name. | `samples/payload.vein` |
| emit | `emit @Hit { amount: 5 }` | Queues an event. It does not deliver right away. Omitted fields are filled from defaults, then from context (the event being heard, then locals). | `samples/payload.vein` |
| hear | `hear @Hit as h { … h.amount … }` | A handler block. The binding reads payload fields directly, with no sigil. | `samples/payload.vein` |
| Provenance envelope | `s.from.kind · s.from.name · origin · cause · trail` | Fields the runtime attaches to every event: id, from, origin, source, bundle, cause, trail. You never declare them. `veinc events` prints them. | `samples/payload.vein` |
| audience | `hear @E as e audience $Session #Trusted { … }` | A barrier on a handler: it fires only when the emitter carries every listed shape and mark. It is enforced over Vein.Net (signed frames) and only advisory over the local console pipe. | `samples/events.vein` |
| Shard | `shard Drain { each tick { … } settled { … } }` | The only place behaviour lives: a set of schedule and hear blocks. A shard can never be shared or put inside a publicator (VS0108). | `samples/entities.vein` |
| target (identity query) | `target $Health #Enemy as self { self.Health.hp -= 1 }` | Loops over every identity that carries ALL the listed shapes and marks. Fields are read as binding.Shape.field. At least one shape is required (VS0236). Results come in spawn order unless a `by` clause sorts them. | `samples/entities.vein` |
| target (collection) | `target words(s) as w { … }  ·  target rows as row: $Task { … }` | The same verb iterates any list. There is no for/in. An optional `: $Shape` ascription declares what outside data (JSON, DB rows) looks like, so its fields are checked. | `samples/loops.vein` |
| run once | `run once { … }` | A schedule that runs once at start. This is where worlds are seeded. `run` and `once` are contextual words, not keywords. | `samples/entities.vein` |
| each tick / each frame | `each tick { … }` | A schedule that runs every simulation tick. The clock is explicit: `veinc run … --ticks N`. | `samples/entities.vein` |
| settled | `settled { … }` | Runs after the tick's fold contributions are reconciled. This is the only correct place to read final values, such as death checks. | `samples/entities.vein` |
| every N | `every 2 { … }` | A wall-clock timer, in seconds. | `samples/console_broadcast.vein` |
| folds | `hp: int folds sum` | A field modifier that says how writes from several shards in one tick combine: sum, min, max, replace, first, all, any. It accumulates across ticks and does not recompute. | `samples/entities.vein` |
| attach / unattach | `attach $Health to e { hp: 5 }  ·  unattach $Health from e` | Adds or removes a component. The change is deferred to the commit point, so it is invisible inside the event that made it and visible from the next one. | `samples/entities_detach.vein` |
| destroy | `destroy self` | Removes an identity. The removal is deferred like the other structural changes. | `samples/entities_destroy.vein` |
| Index | `Index` | The nearest loop's 0-based iteration counter, in target and repeat. Where `Entity` says which identity, `Index` says which iteration. It does not sort anything. | `samples/entities_index.vein` |
| SF (shard function) | `SF announce(label: string, value: int) { emit @E { … } }` | A named sequence of emits that runs inline. It never returns: `-> T` is VS0105 and `return` is VS0107. | `samples/functions.vein` |
| fn | `fn fib(n: int) return int { … return … }` | A function that computes and returns a value. It can be called in any expression, and across bundles when shared. | `samples/functions.vein` |
| builder | `builder Button { label: string   markup = "<button>" + label + "</button>" }` | A reusable template. Its members are its parameters, with no ( ) parameter list. Its output field decides what it makes. A builder cannot hold statements. | `samples/mypage.vein` |
| bring | `bring Button("+1")  ·  bring 3 Card(…)` | Instantiates a builder, binding arguments by position. The fragment it produces is queued, not written. A leading count repeats it. | `samples/mypage.vein` |
| Output-channel field | `markup = …  ·  css = …  ·  code = …  ·  line = …` | The field NAME picks the channel: @Html, @Style, @Script, @Print. With no such field the builder emits @BuilderName. For this reason these four words cannot be parameter names. | `samples/mypage.vein` |
| $Shape include | `builder Card { $Card   markup = … }` | A compile-time copy of a shape's fields into a builder's or event's parameters. It attaches nothing: `target $Card` still matches zero identities. | `samples/shaped.vein` |
| Identity template | `builder Unit { $Health $Shield   mark #Unit }  ·  bring Unit(10, 6) as u` | A builder with a `mark` member builds an identity: bring = spawn + attach each shape + mark. `as` binds the identity it built. | `samples/entities_template.vein` |
| Builder variant | `builder BigCoin from Coin { value = 5 }` | Fixes some of a base builder's arguments BY NAME and inherits its marks. A fixed parameter takes no argument. A cycle is VS0239. | `samples/builder_variants.vein` |
| ? fill-the-rest / base | `bring Draft("Untitled", ?)  ·  bring Panel("Danger", base, …)` | `?` fills every remaining slot with its default, or a typed zero when there is none. `base` fills one slot with its declared default without skipping it. | `samples/builder_defaults.vein` |
| ShardView | `ShardView Page { hear @Html as h { … } }` | A First-Class object that ASSEMBLES. It hears fragments and emits the finished artifact, such as the @Response page. | `samples/site.vein` |
| bridge | `bridge Sync { hear @Hit as h { emit @SyncedHit } }` | A shard-like First-Class object that spans a boundary. It shows up as Bridge.Sync in `veinc graph` and in provenance. | `samples/payload.vein` |
| Bundle | `bundle Functions by you { … }` | The module. `by author` roots its qualified name. It is private by default and can span files (publicators/*.vein is API, shards/*.vein is behaviour). | `samples/functions.vein` |
| publicator + shared | `publicator DemoCore { shared("…") shape $Health { … } }` | A publicator is a bundle's API grouping. Only `shared("label")` members can be used from another bundle. The label is shown in completion, and over 160 characters is VS0243. | `samples/demo.vein` |
| need | `need "Vein.Console"  ·  need "Vein.Math" as M` | Names the bundle this one is built on. It lets bare names resolve (lookup order: local → built-in → need) and links the bundle into an app. With `as`, names are imported qualified only (*M.…). `use` is retired (VS0338). | `samples/entities.vein` |
| Qualified star path | `*Vein.Console.Io.@Print  ·  *Vein.Math.Scalars.clamp(…)` | A reference that cannot collide: *Author.Bundle.Publicator.member. It is used for includes, cross-bundle emits, calls and discovery. target and mark take bare names. | `samples/entities.vein` |
| app / load / principal | `app Shop { load "Store.vein"  load "Billing.vein" }` | A manifest listing bundles. The first `load` is the principal and the only one that boots. Every loaded bundle's shards join ONE runtime. | `samples/app_capabilities/shop.app.vein` |
| start | `start @NewGame { seed: 42, players: 2 }` | A bundle's boot event, at most one per bundle. It replaces the default @Request { path }. It can be overridden with `--set k=v` or `load … start { … }`. | `samples/boot.vein` |

## The toolchain

| command | what it does |
|---|---|
| `veinc new <bundle|app> <Name> [--author A] [-o <parentDir>]` | Scaffolds a new bundle or app project on disk. It writes files, so don't run it inside the repo. |
| `veinc check <file.vein>` | Runs the full front end, including Lower where most VS02xx codes are raised, and prints only diagnostics. It prints 'ok' when the file is clean and exits 1 on errors. |
| `veinc tokens <file.vein>` | Lexer output: span, TokenKind and text for each token. It shows sigil folding, `30%` as one Percent token, and the virtual Term at a newline. |
| `veinc ast <file.vein>` | Prints the parsed AST. |
| `veinc ir <file.vein> [--ir-unicode] [--ir-spans] [--ir-full-strings] [--ir=legacy]` | The VeinIR ASCII tree, which is what check-ir.sh compares against golden files. It also reports Lower diagnostics. |
| `veinc run <file|app.vein> [--ticks N]` | A console session: boots the program, pumps stdin/stdout through @Input/@Print, advances N ECS ticks, and runs `every N` timers and the network. An app manifest is linked into one runtime first. |
| `veinc render <file> [path] [--set k=v] [--ticks N]` | One shot: fires the boot event or @Request { path } and prints the emit trace, the HTTP status and the @Response body. No socket is involved. |
| `veinc serve <file> --port N [--host H]` | A real HTTP server over the same @Request → @Response pipeline, with a fresh interpreter for every request. |
| `veinc build <file> [--rid R] [--framework-dependent]` | Builds a standalone .exe that embeds the interpreter and the source, via dotnet publish. `--rid linux-x64` cross-builds for a VPS. It writes an exe. |
| `veinc emit <file|app> -o <dir>` | Translates HIR to readable C# for the SECS backend, covering the identity half: shapes, marks, target, folds, run once/each tick/settled. It reports interpreter-only built-ins such as fromJson and split. |
| `veinc graph <file> [path]` | The First-Class graph from one render: nodes (Shard/Bridge/ShardView/Runtime) and emit edges, e.g. `Bridge.Sync --@local.Demo.SyncedHit-->`. |
| `veinc events <file> [--json]` | Lists every event with each field marked required or default, plus the provenance envelope. |
| `veinc scaffold <file> <@Event | &Builder | Name>` | Prints a ready-to-paste emit body or bring call. Every slot is labelled with its type, the shape it came from, and whether it is required or optional. |
| `veinc symbols <app.vein> [--json]` | Discovery across bundles: every shared member as *Author.Bundle.Publicator.member, with collisions flagged and start signatures shown. |
| `veinc exec <file> [--json] [--ascii]` | The derived execution model, from static analysis: block classes ◆◉◷▣∞, parallel ⚡ / synchronized 🔒 / conflict !, and waves. |
| `.\veinc.cmd <cmd>  ·  dotnet run --project src/Vein.Cli -- <cmd>` | Two ways to invoke the CLI from the repo (a wrapper script or dotnet run). |
| `dotnet build VeinScript.sln` | Builds the compiler, CLI, Workbench, tests and SECS runtime. |
| `dotnet test src/Vein.Tests` | Behaviour tests, including SamplesTests: every sample compiles with zero warnings and every header command is runnable. |
| `bash tools/check-ir.sh` | Compares printed IR trees against golden files (the IR's shape). |
| `bash tools/check-backend.sh` | Compiles the listed samples to C#, runs them, and diffs their output against the interpreter byte for byte (the backend's meaning). |
| `bash tools/check-perf.sh` | Measures backend speed. Release build, past JIT warm-up. |
| `dotnet test src/Vein.Jit.Tests` | The net9 JIT test suite, kept separate because Vein.Tests is net8. |
| `dotnet run --project src/Vein.Workbench` | Launches the Workbench desktop IDE (Avalonia). |

## The Workbench (the IDE)

**VeinScript Workbench**: a desktop IDE (Avalonia). Start it with `dotnet run --project src/Vein.Workbench` or install it with `VeinScript-Workbench-win-Setup.exe`, which installs per user under %LOCALAPPDATA% so the samples stay editable. The first launch opens on the samples, and **Help ▸ Browse Samples** gets back to them later.

**Worth showing on camera:**

- **▶ runs what the file declares.** The file's header line (`// veinc run samples/entities_chance.vein --ticks 4`) becomes an editable command box in the toolbar, so you can change `--ticks 4` to `--ticks 40` and press ▶. Each session shows its exit code and duration (`exited 2 · 1.4s`) and has ↻ to re-run and ⤓ to save the full log.
- **Compile as you type.** About 450 ms after you stop typing, red underlines appear and the Diagnostics list (filterable by severity and text) refreshes. **Quick fixes** exist only where the fix is mechanically certain: VS0228 inserts `?`, VS0218 declares the mark, and VS0338/VS0339 rewrite `use Movement` into `need "kit.Movement"`.
- **Sigil completion**: `$` shapes, `#` marks, `@` events, `&` builders, `*` qualified names, `.` members. Typing `?` right after `emit @E` or `bring B` **expands into the full field list**, with each field's type and the `$Shape` it came from. A signature-help strip marks the current slot in a `bring`.
- **Navigation across bundles**: F12 (it works on a `need` line too), Shift+F12 to find references, Ctrl+T to search symbols, Ctrl+Shift+F to find in files, the Outline pane, and Alt+←/→ to go back and forward.
- **Runtime panel: the killer demo.** A tick stepper, an event timeline and an entity browser. Boot the world, step one tick at a time, and watch identities and their components change. This replaces a line debugger, because shards never call each other.
- **Execution tab** (the `veinc exec` model): each block gets a badge (◆ Event, ◉ Reactive, ◷ Scheduled, ▣ Frame, ∞ Continuous) plus ⚡ parallel / 🔒 synchronized / ! conflict, laid out in waves. It shows that `folds sum` is what makes two shards safe to run in parallel.
- **Events tab**: who emits and who hears each event, with a jump from every row. It flags events that are emitted but never heard, and heard but never emitted.
- **IR Tree / Raw IR**: double-click a node to land on the source line that produced it.
- **Terminal**: several concurrent sessions, each with its own stdin. **Run All Participants** (Ctrl+F5) starts `control_center.vein`'s Control → Alpha → Beta in header order. The **Consoles** topology shows who addresses whom and flags unresolved sends in red. **Live** shows the bound pipes, and **Transcript** interleaves all sessions with timestamps.
- **Preview** for websites: a route picker built from the site's own `if r.path == "…"` conditions, the rendered markup with status and headers, Open in Browser, one-click `serve`, and live reload.
- **Project Explorer** for an `app.vein`: ★ marks the principal and 📦 its dependencies. The **Bundle Inspector** shows a PUBLIC/SHARED/PRIVATE bar. The **Symbols** tab lists every primitive under the author and bundle that brought it, with collisions highlighted.
- **Build ▸ Publish Executable** (runs `veinc build`), **Run Checks** (check-ir.sh, check-backend.sh, …) from a menu, and **New Project** templates for a CLI app, chat app or website.
- The UI also has an **Assistant** panel (sign-in; every suggestion is compiled before an Insert button is offered) and a **Lounge** panel (a shared chat room). They are not described in docs/WORKBENCH.md, so check both live before putting them in the video.
- Not there: an embedded web view (C1b, deliberately left out; Open in Browser covers it).

## Reserved but not implemented

- mute: lexed only, with no parser reference. `mute A` in a tick block → VS0104 "Unexpected 'mute' in expression".
- unmute: lexed only. `unmute A` → VS0104.
- transform: lexed only. At bundle level → VS0102 "Unexpected 'transform' at declaration level".
- on: lexed only. `on click { }` in a shard → VS0103 "Unexpected 'on' in shard body". It is still legal as a field name (samples/sigil_names.vein `shape $Switch { on: int }`).
- sync: lexed, and CanEndStatement knows it, but no parser case. `shard A sync {` → VS0100, in a shard body → VS0103, in a tick block → VS0104, even though LANGUAGE.md/KEYWORDS.md describe it.
- count: lexed only. `let n = count $H` → VS0104. It is still fine as a field name (entities_tree `count: int folds sum`), and the size of a list is `len(x)`.
- map: lexed, but `map<string,int>` in type position → VS0100 "Expected type, found KwMap".
- use: lexed and parsed only so it can be rejected. Every use is VS0338 telling you to write `need "Author.Bundle"` (retired rather than unbuilt).
- NOT unimplemented, despite what the docs say: `enum` works inside a shape (samples/enum_state.vein runs; only top-level is VS0102, by design D11); `random` is no longer a keyword and `random()` works; `bridge`, `audience`, `builder`, `bring`, `base`, `ShardView`, `Index`, `need` and `app` are all implemented.
