What you settled

Licence
Open source always. Selling what you build with it, always allowed.
Removal
No delete. Modification only, and takedown by moderator review.
Identity
Email plus a unique pseudonym, set at signup on the website.
Publish unit
The whole folder, with entry_path naming the way in.

Two things that follow, and need your eye

Deleting an account must not delete its bundlesderived

Supabase cascades auth.users into profiles. If projects.owner cascaded as well, one person closing their account would take out every bundle a hundred other projects had come to depend on — the exact outcome the no-delete rule exists to prevent.

So owner is ON DELETE SET NULL, and a separate owner_handle column carries the name forward. An orphaned project is still readable, still compiles, and is visibly unowned.

There is no private visibilityderived

A project switched to private after publication vanishes for everyone already using it. That is deletion wearing a different word, and it walks straight around the moderator.

So visibility is public or unlisted only. Unlisted keeps a project out of search and listings while a direct link still resolves — as far as taking it back can go without breaking dependents.

The public half of an account. Supabase Auth owns the private half.

A row is created by a trigger on auth.users insert, reading the handle out of the signup metadata — so a signup can never leave an account with no profile and no name. The Workbench never sees this path: it signs in, and its Create an account button opens the browser at the VeinScript site.

project_files

corpus · immutable

The source itself, as text columns — because a corpus in text is a corpus you can search.

ColumnTypeWhy
version_iduuid → project_versions
pathtextunique(version_id, path). Relative, forward slashes, and checked: no .., no leading slash, no drive letter. A path check is what stops a restore writing outside the folder you chose.
contenttext, ≤ 512 KBNot Supabase Storage. .vein files are small, and text columns are what make full-text search across every published bundle possible.
bytesint
sha256textSo a re-publish can show what actually changed, and a restore can prove it got the same bytes.

Whole folder means whole folder: everything ProjectPackage finds under the root — the main file, publicators/ and shards/ fragments, bundles/ dependencies, .veinproj, vein.discovery — minus bin/, obj/ and out/. Ordered StringComparer.Ordinal, so publishing an unchanged project twice produces identical hashes.

The licence list

Every published version is open source, and every option below lets whoever uses your bundle sell the game, app or site they build with it.

MIT default
Shortest, most permissive, what anyone expects. Keep the notice, do what you like.
Apache-2.0
MIT plus an explicit patent grant. Choose it if patents could ever come into it.
BSD-3-Clause
MIT-equivalent, with a clause against using your name to endorse their product.
MPL-2.0
Weak copyleft: changes to your files stay open, the product built around them can be closed and sold.
Unlicense
Public domain dedication. No notice to keep, no conditions at all.
CC0-1.0
The same intent as Unlicense, with a licence fallback for countries where dedication is not a thing.
GPL-3.0 and AGPL-3.0 are deliberately off the list. They permit selling too — but they require the whole derived work's source to be released. A bundle under one would quietly force every game and web app built on it to open its own source, which is the opposite of what you asked for, and not a trap to leave a stranger to discover after they have shipped.

Removal

takedown_requests

moderation

The only route to removal. Nothing in the corpus is deletable by its owner.

ColumnTypeWhy
iduuid PK
project_iduuid, nullableA whole project…
version_iduuid, nullable…or one bad version. Exactly one of the two is set.
requesteruuid → profilesMay be the owner asking for their own code back, may be someone reporting a problem.
reasontext NOT NULL, 10–2000A request with no reason cannot be judged, so the database refuses one.
statustext default 'pending'pending · approved · rejected. Only a moderator can move it off pending.
decided_byuuid → profilesWhich moderator. A takedown with no name attached is not reviewable.
decided_at / decision_notetimestamptz / text
created_attimestamptz

The DELETE policies on projects, project_versions and project_files exist for moderators and nobody else, checked through an is_moderator() SECURITY DEFINER function — so the policy never has to read profiles under the caller's own RLS.

The reasoning is yours and worth writing down: if a hundred projects load your bundle, your right to withdraw it stops where their working build begins. A moderator is the only place that judgement can actually be made.

Polled, not streamed — and the primary key is what makes polling exact.

ColumnTypeWhy
idbigint identity PKNot a timestamp. The client asks ?id=gt.<last>&order=id.asc — no clock skew, no ties, no message fetched twice or missed. A created_at poll has all three failure modes.

Reading is authenticated as well as posting, per authenticate before chatting — a signed-out Workbench makes no chat request at all.

Row Level Security

The anon key ships inside the Workbench, so RLS is not a layer of the security model, it is all of it. Every table is created with its policies in the same migration file — a separate rls.sql is a file someone forgets to run, and the cost of forgetting is a public database.

TableSelectInsertUpdateDelete
profiles anyone self self, not role none
projects anyone owner owner moderator
project_versions anyone owner immutable moderator
project_files anyone owner immutable moderator
takedown_requests requester · mod signed in moderator none
rooms signed in none none none
messages signed in self own own, soft

Listings filter visibility = 'public' in the query rather than the policy, so an unlisted project still resolves by direct link. The last migration file is 0099_checks.sql: negative tests you run against a fresh project with the anon key alone, proving that posting as another user and updating someone else's version both fail.

Still open

  1. Is unlisted enough, or should a published project be permanently listed and only removable by a moderator? Right now an owner can quietly unlist without review.
  2. Who is the first moderator? The migration can seed your account by handle, or leave the table empty until you promote someone by hand in the SQL editor.
  3. Rate limits. Nothing currently stops one account posting a thousand messages or publishing five hundred versions. A per-minute check is cheap to add now and awkward to retrofit — worth doing, unless you would rather see how it behaves first.
  4. The site's URL, for the Create an account button and for CloudConfig.
